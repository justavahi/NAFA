# Первый сквозной прогон

Реализованы все 17 задач PE, сборка карточки, независимый критик,
ограниченный ремонт и адаптеры backend/DA. Воспроизводимые замеры на API —
в [отчёте](evaluation/acceptance_summary.md).

## Попробовать без ключа

Из корня NAFA:

```bash
uv sync --dev
uv run python -m pe.run replay examples/demo/case.json --responses examples/demo/responses --out out/demo
```

Результаты: `out/demo/preview.md`, `card.json`, `result.json`,
`requests/PRM-05.json`, `PRM-06.json`, `PRM-07.json`.

Демо полностью синтетическое. Ответы моделей и результаты DA в нём заданы
вручную, `is_mock=true`. Реплей проверяет прохождение данных и работу проверок,
не измеряет качество, стоимость или задержку LLM. Даже при всех успешных
проверках у реплея `publishable=false`, исполненная модель и токены равны null.
Примеры не включены в few-shot промптов и не являются золотым набором.

## Что принимает запуск

`CaseInput` (`pe/pipeline.py`):

- `ledger`: проверенный реестр новостей, позиции банка и агрегированных признаков;
- `event`: уже извлечённое событие EventExtraction от backend/PRM-01;
- `persona`, `bank_view_status`;
- `relevance_id`, `confidence_id`: ссылки на значения FM-06 и FM-20 из DA;
- `effect_source_ids`: фактор → ID готового расчётного знака эффекта.

Цепочка исполнения сейчас состоит из трёх вызовов: PRM-05 → PRM-06 → PRM-07.
PRM-01 исполняется отдельно через `pe.tasks.run_task`; его выход передаётся в CaseInput.
Приём новости по URL, расчёты DA и поиск источников остаются в их компонентах.

## Что проверяет код

- Совпадение источников, цитат, слоя и клиента; отсутствие циклов в расчётах.
- Известный признак в «почему это вам», совпадение структурного знака эффекта.
- Числовые токены только из процитированных доказательств: запятая и точка
  нормализуются, единицы и знаки сравниваются отдельно, эквивалентные записи дат нормализуются. Смысл, субъект
  и соответствие текстового вывода знаку проверяет независимый критик.
- У критика обязательны все исходные claims, правильные слои, подтверждающие
  ссылки, отсутствие замечаний по числам и ответы на все шесть вопросов.
- Уверенность и релевантность вставляет сборщик из DA; PRM-15 пропускает предложение только через отдельное правило BA.

Начальная уверенность FM-20 передаётся из расчётного контура. Если модель
добавляет фактор вне рассчитанных DA знаков или общую фразу без признака
клиента, сборщик удаляет такой фрагмент и отмечает частичный результат.
При иных замечаниях выполняется один ограниченный ремонт; после повторной
ошибки карточка блокируется (`needs_fix`). Числовая уверенность не изменяется
моделью. Ограничения и unknowns сохраняются в trace и preview.

## Подключить реальные модели

Для локальной интеграции можно экспортировать точную версию существующего
шлюза без слияния веток:

```bash
uv run python scripts/prepare_backend.py
uv sync --dev --extra backend
```

Экспорт лежит в игнорируемой `.local/backend/store`; исходная ревизия —
`1e794c8b037b63c4fcbd5c34caeaaf72c8f33f04`. Повторный экспорт не перезаписывает
локальные настройки. Этот snapshot не содержит парсеров и полного backend.

Нужны:

1. `.env` с `LLM_BASE_URL` и `LLM_API_KEY` общего шлюза организаторов.
2. Подтверждённые `api_name` и положительные тарифы RUB/1000 токенов в
   `.local/backend/store/config/models.yaml`. Для платного шлюза нулевые заглушки отклоняются.
3. Путь к существующей общей SQLite-базе backend, чтобы бюджет и кэш
   учитывались вместе с остальными вызовами команды.
4. Реальный `case.json` из backend/DA, без mock-документов.

```bash
uv run --env-file .env --extra backend python -m pe.run live path/to/case.json --backend-root .local/backend/store --db /absolute/path/to/shared/nafa.db --organiser-budget --out out/live
```

В штатной интеграции можно вызвать `run_case(case, gateway_adapter)` прямо
из приложения backend и использовать его настроенный LLMGateway.
Маршруты: GLM-5.3-Flash (`reasoning`) для PRM-05/06 и Qwen3.6 35B A3B (`general`)
для PRM-07. Шлюз должен вернуть указанное имя модели, иначе запуск отклоняется.

После получения инструкции точные API ID закреплены в `config/organiser_models.json`.
Для документированного шлюза с серверным лимитом 500 ₽/сутки можно добавить
`--organiser-budget`: при неизвестных тарифах он отслеживает токены и сохраняет
стоимость как `null`, а денежный лимит обеспечивает сервер организаторов.
На произвольном адресе этот режим запрещён.

### Если модели запущены локально

Backend содержит HTTP-клиент, а не сервер инференса или веса моделей.
Он может подключаться и к локальному серверу с совместимым API. Для этого
задайте `LLM_BASE_URL` (например, `http://127.0.0.1:11434/v1`), настройте
`api_name` именно установленных разрешённых моделей и добавьте `--local` к
команде live. В этом явном режиме на loopback-адресе ключ необязателен и
допускаются нулевые тарифы за токены; стоимость оборудования не оценивается.
Наличие Ollama или произвольной модели Qwen не означает наличие точной модели,
разрешённой кейсом. Установка и запуск весов в этот каркас не входят.

Код использует кэш, тарифы, бюджет и сетевые повторы существующего шлюза.
Новых сетевых клиентов нет. На уровне PE обычно три вызова; схема исправляется не более одного раза,
карточка — за один общий цикл, общий лимит восемь. Повторный поиск требует
переданного хостом callback. Сетевые повторы самого шлюза могут увеличить
число HTTP-запросов. Наследуется его проверка уже потраченного бюджета перед
вызовом; предварительного резервирования стоимости ответа в нём пока нет.

Запросы и результаты в `out/` могут содержать переданный контекст компании;
эта папка игнорируется Git. В модель передаются псевдонимы и агрегаты.
