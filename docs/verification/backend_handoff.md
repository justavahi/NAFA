# Подключение PE к объединённому бэкенду

Из корня репозитория:

```bash
uv sync --project src/store --group dev --frozen
# Настройте src/store/.env по .env.example: API URL/ключ, admin token и постоянную соль псевдонимов.
python scripts/run_backend.py
```

Сервер: `http://127.0.0.1:8000`, OpenAPI: `/docs`. Модели вызываются через
общий `app.llm_gateway.LLMGateway`, SQLite/кэш/бюджет — из конфигурации Backend.
PE не создаёт отдельную базу вызовов. Точные ID разрешённых моделей исправлены
в `src/store/config/models.yaml`; нулевые RUB-тарифы означают неизвестные цены.

Приложение с интерфейсом открывается по `/`. PE factory включает автоматический
`ProductionProvider` и авторизацию. Подготовка runtime описана в корневом README. Старый запуск
`python -m app.cli serve` или `python scripts/run_backend.py --mode baseline`
оставляет предварительный оркестратор на правилах: `publishable=false`.
Корневой Docker Compose запускает PE/DA/UI. Исторический Compose внутри store — baseline.

## Договор между DA/backend и PE

Вход — `CaseInput` с полным реестром доказательств:

- Backend даёт сохранённый текст события, ID, метаданные и проверенные цитаты банка.
- Извлечение даёт `EventExtraction`: тип, факты, факторы и направления.
- DA даёт агрегаты клиента, готовые FM-06/FM-20, знаки эффекта и зависимости расчётов.
- В `ledger.client_id` — `app.util.pseudonym(client_id)`, такой же псевдоним в признаках.
- NEWS-документ имеет ID события из Backend и ровно его сохранённый `text` или `snippet`.
  Текст повторно проверяется перед генерацией; изменившийся источник аннулирует заготовку.
- Для исторического `as_of` не допускаются будущие события или датированные источники.
  Неизвестные даты клиентских агрегатов не становятся доказательством исторической точности.

Схемы: `src/report_scripts/schemas/CaseInput.json`, `PreparedCase.json`,
`RegistrationInput.json`. Сырые платежи, связи с физлицами и непроверенные поля
не должны попадать в этот договор; проектирование агрегатов остаётся у DA/backend.

Регистрация проверенного входа — внутренний endpoint:

```bash
curl --fail-with-body http://127.0.0.1:8000/internal/pe/cases \
  -H 'Content-Type: application/json' \
  -H "X-Admin-Token: $NAFA_ADMIN_TOKEN" \
  --data-binary @prepared_request.json
```

`prepared_request.json` содержит поля `client_id`, `event_doc_id`, `as_of`
и `prepared: {case: <объект CaseInput>, selected_news_ids: null}`. Это описание
структуры, не подставной готовый реальный кейс. Файл должен сформировать доверенный
расчётный контур. Не регистрируйте демонстрационные значения как реальные.

Альтернатива без HTTP: `register_prepared_case(conn, ..., pseudonym=app.util.pseudonym)`.
Для генерации на лету можно передать `case_provider` в `BackendBridge` или
`pe.backend_app.create_app`. Provider получает `conn, client_id, event_doc_id,
persona, as_of` и возвращает `PreparedCase`. По умолчанию установлен ProductionProvider:
проверяет ревизию DA, извлекает произвольную новость, рассчитывает формулы DA и
строит реестр. Ручная регистрация для стандартного пути не нужна. После изменения
записи клиента устаревший профиль отклоняется до повторного импорта агрегатов.
Неизвестные знаки влияния используют UNKNOWN_EFFECT, без фиктивного FM-14.

Заготовки разделены по клиенту, событию, роли и `as_of`. При обновлении агрегатов
их нужно пересчитать и перерегистрировать: хранение заготовки само по себе
не гарантирует актуальность клиентских данных.

## Доступ

`POST /session` с `{token}` создаёт HttpOnly SameSite-cookie на 8 часов;
`DELETE /session` завершает сессию. API принимает также `Authorization: Bearer <код>`.
NAFA_CLIENT_TOKENS связывает коды с ID компаний; X-Admin-Token сохранён.
Клиенту недоступны чужие компании, карточки, BYO, admin API и бюджет.
При ingest администратор указывает client_id либо явный shared:true.
Главная страница и public-config открыты; demo-коды выдаются только для
синтетических профилей при явном NAFA_DEMO_MODE=true. В рабочем режиме коды скрыты.

## Публичный сценарий после подготовки входа

1. `POST /cards/generate` — прежний body `{client_id, persona, event_doc_id}`
   либо `query` вместо `event_doc_id`. Клиент не передаёт prompt/модель/реестр.
2. `GET /cards/{card_id}` — сохранённая карточка.
3. `POST /cards/{card_id}/ask` с `question` — GLM пишет ответ, Qwen проверяет.
   Если задан `scenario`, вычисление остаётся детерминированным кодом FM-15.
4. `POST /cards/{card_id}/feedback` и `GET /cards/{card_id}/trace` — прежние адреса.

Успех: `status=verified`, `publishable=true`, `partial`, `unknowns`,
`discarded_claims`, слои/ссылки и trace. Частичный результат нельзя скрывать в UI.
FM-06 не подменяет рейтинг FM-13: пока отдельный DA-рейтинг не передан, `score.score=null`.

Блокировка: HTTP 409 с `status=withheld`, `publishable=false`, `card=null`, `trace_id`.
Непринятые карточки не попадают в публичную таблицу `cards`; непроверенные ответы
не попадают в `card_questions`. Аудит сохраняется отдельно в `pe_runs`.
Replay/evaluation не публикуются как рабочие карточки. При явном NAFA_DEMO_MODE=true
evaluation отображается со статусом demo и publishable=false; replay всё равно запрещён.
Отсутствует импортированный профиль — 422 PE_PROFILE_NOT_READY; клиент/событие — 404. Нет автоматического
возврата к тексту на правилах под видом проверенной AI-карточки.

Для новой версии с ограниченными фрагментами можно явно задать
`NAFA_PE_PROFILE=role_focus_v2` и передать проверенные атомарные `selected_news_ids`.
Для автоматически собранных входов применяется connected_v1 (PRM-06 v9 и UNKNOWN_EFFECT).
Для ручных входов без profile сохранён прежний production manifest. Качество connected_v1
ещё не принято на живых моделях; выбор этого профиля — реализация нового входного контракта.

## Что проверено и что ещё не закрыто

`GET /cards/{card_id}/basis` возвращает признаки компании и расчёты из
сохранённого реестра карточки. Применяется та же проверка владельца, что для
`/trace`; сырые записи клиента, платежи и связи не возвращаются.
Во вкладке «Как получен вывод» этот контекст показан рядом с этапами проверки.

HTTP-тесты `src/store/tests/test_pe_connection.py` используют настоящий API,
общую БД и настоящий шлюз, но контролируемые ответы моделей через MockTransport.
`scripts/check_server_startup.py` поднимает настоящий Uvicorn на TCP и проверяет
админ-регистрацию и блокировку mock-источника без единого обращения к модели.

Это не оценка качества рекомендаций и не подтверждение наличия локальных весов.
Case provider, DA-ранжирование, интерфейс и изоляция клиентов реализованы.
Браузерный путь подтверждён в browser_check.json с контролируемыми ответами моделей.
Остаются повторный поиск по решению критика, внешний запуск Docker, живой прогон
нового профиля, сверка PDF и независимая человеческая приёмка.
