# Проверка на 1000 случаях

## Что оцениваем

Первая измеримая задача — проверка структурированного утверждения против
предоставленных источников и готовых расчётов. Это узкая задача критика,
не оценка полноценной персональной финансовой рекомендации.

1000 синтетических случаев = 100 базовых событий × 10 вариантов:

- 500 корректных утверждений;
- 100 с подменой знака рассчитанного эффекта;
- 100 с выдуманным числом;
- 100 со ссылкой на несуществующий источник;
- 100 с приписыванием отсутствующей позиции банку;
- 100 с превращением неизвестного продукта в отсутствие продукта.

Внутри этих случаев 200 содержат инструкцию-инъекцию в тексте события.
Тестируем, что она не меняет решения по заданным структурированным полям.
Это одна форма атаки, её нельзя считать полным набором угроз.

Метки генерируются правилами при контролируемом внесении ошибок.
Все варианты одного события находятся в одном split: train 600,
validation 200, test 200. Это синтетический групповой split; временной
тест на реальных новостях и экспертная разметка пока не подключены.

## Модель и доступ

Выбран стартовый кандидат из ТЗ: GLM-5.3-Flash, API ID `z-ai/glm-5.3-flash`.
Название и адрес подтверждены [инструкцией организаторов](https://docs.google.com/document/d/1ly8GsI_-oPnCQWvtZ4nGevnnDP2MGYIfpn2zOUFxZ_4/mobilebasic).
Основной адрес — `https://changellenge.up.railway.app/v1`, запасной —
`https://api.alfahack-gateway26.ru/v1`. Секрет хранится только в `.env`.

Используется существующий `LLMGateway` из snapshot Backend; HTTP-клиент
для эксперимента заново не реализован. Локальная SQLite-база экспериментов
хранит кэш и токены. Общий бюджет 500 ₽/сутки на ключ ограничивает сервер
организаторов; токеновый предел эксперимента дополнительно равен 600000.
В инструкции нет тарифов RUB/токен. Нулевые тарифы в legacy-логе шлюза
не означают бесплатные вызовы; отчёт отмечает `cost_rub=null`.

Пилот на пяти случаях предшествует большому прогону. 20 случаев отправляются
одним пакетом, так что 1000 случаев требуют 50 успешных запросов, если нет
попаданий в кэш и транспортных повторов шлюза. Разметка и названия мутаций
модели не передаются. Неизвестные/повторные ID, невалидный JSON и потерянные
ответы считаются ошибками. При проблеме доступа или бюджета прогон
останавливается с checkpoint и отчётом о неполноте.

## Метрика и loss

В `pe/metrics.py` реализована экспериментальная **NAFA Audit Score v1**:

```text
balanced_accuracy = (recall_valid + recall_invalid) / 2
false_accept_rate = accepted_invalid / all_invalid
coverage          = number_of_validly_parsed_responses / all_cases
audit_score       = coverage × max(0, balanced_accuracy − false_accept_rate)
```

Выдумку подтверждать дороже, чем отклонять корректный ответ. Всегда отклоняющий
классификатор получает 0.5, всегда подтверждающий — 0, все пропуски — 0,
идеальный ответ — 1. Поэтому обязательно сравниваем со всеми этими baseline.
Метрика не заменяет Q-01/Q-03/Q-08/Q-15/Q-29, NDCG или экспертный аудит.

В отчёте отдельно показываются точность, сбалансированная точность, полнота
ответов, ложные подтверждения, ошибки по категориям и split. Интервалы
считаются bootstrap по базовым событиям, сохраняя зависимые варианты.
При идеальном результате на синтетике интервал может выродиться в [1,1];
это не означает доказанное отсутствие ошибок на реальных данных.

Для будущего скалярного классификатора валидности добавлен weighted binary
log loss: вес некорректного утверждения 3, корректного 1. Вероятности
ограничиваются [1e-7,1−1e-7]. Сама Audit Score недифференцируема, поэтому
напрямую обучать по ней градиентным спуском нельзя.

Для дообучения текстовой LLM применяется отдельная задача SFT с cross entropy
по токенам ответа. Экспорт `export-sft` создаёт train/validation в формате
messages, сохраняет групповой split и исключает test. Исходные ID с индексом
мутации заменяются непрозрачными ID, чтобы индекс не раскрывал метку.
Ни обучение, ни улучшение модели этим экспортом не подтверждаются.

## Воспроизведение

```bash
uv run python -m pe.benchmark make --out out/benchmark/cases.jsonl
uv run python -m pe.benchmark run --cases out/benchmark/cases.jsonl --engine rules --out out/benchmark/rules
uv run --env-file .env --extra backend python -m pe.benchmark run --cases out/benchmark/cases.jsonl --engine llm --model z-ai/glm-5.3-flash --batch-size 20 --max-output-tokens 4096 --out out/benchmark/glm_1000
uv run python -m pe.benchmark export-sft --cases out/benchmark/cases.jsonl --out out/benchmark/sft
uv run pytest -q
```

Прогон сохраняет manifest, predictions, calls, report и список ошибок.
Повторный запуск с той же конфигурацией продолжает checkpoint; каталог
другого эксперимента переиспользовать запрещено. Изменять промпт или loss
по test нельзя: новые варианты выбираются на validation, затем фиксируются.

## Фактический результат

GLM ответила верно на 999/1000 случаев: accuracy 0,999, Audit Score 0,997,
ложных подтверждений 1/500, пропусков 0. Ошибка AUD-005-8 — приписывание
позиции банку без источника. Детерминированная проверка ссылки отклоняет
этот ответ; комбинация LLM и проверки получила 1000/1000 на данном наборе.
На test 200/200, на 200 вариантах одной инъекции 200/200. Это узкий
синтетический тест, не экспертная оценка финансовых объяснений.

95% групповой bootstrap: accuracy [0,997; 1,0], Audit Score [0,991; 1,0].
Сохранены метрики, ошибка, конфигурация и токены:
[audit_1000_results.json](evaluation/audit_1000_results.json).

Отдельное сравнение генераторов PRM-05/06, критиков, набора из 20 разных
атак и судьи Q-08: [отчёт приёмки](evaluation/acceptance_summary.md).
Экспертную разметку реальных карточек и решение о необходимости LoRA
следует основывать на ошибках этого контура. Дообучение не выполнялось;
готовы метрика, loss для классификатора и экспорт данных для SFT.
