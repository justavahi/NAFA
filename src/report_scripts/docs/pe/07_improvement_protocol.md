# Улучшение интерпретации без настройки под судью

Базовая версия PRM-06 v4 сохранена в `prompts/profiles/baseline_v1.json`.
Кандидат v5 находится в `candidate_v1.json`. Рабочий `manifest.json` продолжает
использовать v4 до подтверждения качества. Старые результаты не переписываются.

## Что меняется в кандидате

Вместо свободного текста каждого канала модель возвращает пять коротких шагов:
событие, механизм передачи, известный признак компании, условное последствие,
условие пересмотра вывода. В каждом шаге свои `source_ids`; число из другого
шага не считается подтверждением. Следствие обязательно ссылается на готовый
знак DA, признак компании — на COMPANY_FEATURE. Рендерер собирает обычную
карточку; независимый критик проверяет именно показанный текст.

Действия связываются с существующими механизмами: что проверить и какую
развилку разрешит ответ. Их от одного до четырёх по необходимости. Точное
дублирование следствий и повтор одного фактора блокируются; смысловую
различимость дополнительно проверяет критик. Неполные данные не восполняются.
Нового отдельного LLM-вызова для плана нет.

## Фиксация опыта

`python -m pe.improvement prepare --out out/improvement_v1` сохраняет протокол,
точные профили промптов, хэши кода и данных, правила оценки и бюджет до первого
вызова. Изменённый код/промпт требует нового эксперимента. Название версии,
оценки судьи и целевой балл не передаются генератору.

Подготовлено 60 новых **синтетических** сочетаний в десяти семействах сюжетов:
24 dev, 18 validation, 18 test. Семейство целиком относится к одному набору;
клиенты и тексты новостей между наборами не пересекаются. Это десять сюжетных
семейств с вариациями, а не 60 независимых реальных наблюдений. Знаки DA и
данные компаний заданы как fixtures; качество настоящего DA здесь не измерено.
Позиция банка в этих новых случаях отсутствует явно; её обработка дополнительно
покрывается прежними регрессиями. Реальные данные и экспертная выборка нужны
для подтверждения переноса.

Для ограниченного первого прогона **заранее** выбраны три dev-случая: полный
профиль, неполный профиль, смешанная позиция — из разных семейств. Для следующего
этапа заранее выбраны три validation и три test-случая из других семейств.
Неиспользованные варианты остаются резервными регрессиями; не объявляются
протестированными. Контрольный набор не оценивается в пилоте.

## Судья и метрики

PRM-16 v2 фиксирует якоря каждой оси и оценивает лучший обоснованный ответ при
данных, реально доступных на входе. Он не требует неизвестных сумм эффекта,
договоров и лишних каналов. Приложение считает среднее пяти осей; исходный
`overall` сохраняется. Старые 4.125 из v1 напрямую с новой шкалой не сравниваются:
старый и новый генераторы оцениваются заново одинаковой рубрикой.

Предусмотрены Kimi и DeepSeek — оба другого семейства, чем генератор GLM.
Два судьи сами по себе не устраняют переобучение. Основные меры — фиксированные
правила, отдельные наборы и ручная проверка. Парное сравнение скрывает версии
и выполняется в обоих порядках. Несогласие при перестановке считается
неопределённым результатом, а не победой. Рецензентам дают только
`human_review.jsonl` и пустой CSV, без ключа, оценок моделей и общего отчёта.

Отчёт включает медиану, среднее, долю ≥4.5, покрытие оценками, ошибки генерации,
частичные ответы, оба порядка сравнения, токены и тайм-ауты. При трёх случаях
оценка только описательная: статистический вывод о достижении 4.5 не делается.
Автоматического продвижения кандидата в production нет.

## Запуск

```bash
uv run python -m pe.improvement prepare --out out/improvement_v1
uv run --env-file .env --extra backend python -m pe.improvement generate --out out/improvement_v1 --variant baseline
uv run --env-file .env --extra backend python -m pe.improvement generate --out out/improvement_v1 --variant candidate
uv run --env-file .env --extra backend python -m pe.improvement evaluate --out out/improvement_v1 --judge DeepSeek-V4.1-Flash
uv run --env-file .env --extra backend python -m pe.improvement evaluate --out out/improvement_v1 --judge Kimi-K2.6
uv run --env-file .env --extra backend python -m pe.improvement pair --out out/improvement_v1
uv run python scripts/publish_improvement_report.py --run out/improvement_v1
```

Первый опыт ограничен 48 обращениями к шлюзу и 180000 дополнительными токенами.
Лимит общий для параллельных процессов, с предварительным резервированием;
остановка не повышает его автоматически. Шлюз использует прежнюю общую базу,
суточный локальный предел 3 млн токенов и серверный предел организаторов
500 ₽. Тарифы неизвестны; цена не приравнивается к нулю. Общий тайм-аут вызова
120 секунд. При ошибке доступа/шлюза опыт останавливает новые вызовы;
результаты не заменяются повторным выбором удачного ответа.

`--split validation` использует зарегистрированные validation-случаи. `seal`
проверяет полноту их оценки обоими судьями и фиксирует хэши; только после этого
допустим `--split test`. Изменение результатов validation после фиксации
блокирует test. Для расширенной проверки нужен новый явно заданный бюджет;
пилотный лимит не рассчитан на автоматический прогон всех наборов.

## Исправление формата после первого пилота

В v5 один из трёх dev-случаев не прошёл проверку: общий шаблон ремонта JSON
конфликтовал с вложенными EvidenceStep. Неуспех сохранён в
[evaluation/improvement_v1](evaluation/improvement_v1/summary.md).
Обработчик стал учитывать схему; v6 дополнительно требует сохранять объекты
шагов при исправлении замечаний критика. Это изменение формата, рубрика v2
осталась прежней. Ни validation, ни test для этой правки не оценивались.

Второй опыт создаётся командой:

```bash
uv run python -m pe.improvement prepare --out out/improvement_v2 --baseline-run out/improvement_v1 --candidate-profile candidate_v2.json
```

Проверенные базовые ответы переносятся только при совпадении набора, входных
хэшей и базовых промптов. Сохраняются исходные вызовы и ссылка на прежний опыт;
перенос не объявляется новым API-вызовом. Кандидат генерируется и оценивается
отдельно. Бюджет второго опыта не повышается автоматически.
