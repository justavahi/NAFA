Read this first. Every command is detailed in `1_GUIDE_pip.md` (pip) or `2_GUIDE_uv.md` (uv) —
pick one; you do not need both.

## 0. Where is the database? (short answer)

| | |
|---|---|
| **Default file** | **`data/nafa.db`** inside the project folder, e.g. `/home/you/nafa-backend/data/nafa.db` |
| Created by | the first command you run (any command, e.g. `python -m app.cli init-db`) — **nothing to download** |
| Side files | `data/nafa.db-wal` and `data/nafa.db-shm` (normal, SQLite WAL mode; copy/back up **all three together**) |
| Change location | set `NAFA_DB_PATH` in `.env`; a relative path is resolved against the **project folder**, not your current directory |
| Check the real path | `python -m app.cli db-info` (uv: `uv run python -m app.cli db-info`) |
| In Docker | **`/data/nafa.db`** inside the containers, on the named volume `nafa-data` (not in your project folder unless you switch to a bind mount — see guide section 9.5) |
| Committed to git? | **No.** `data/*.db*` is git-ignored; the DB is rebuilt by running the commands below |

Everything else also lives under `data/`:

```
data/
  nafa.db (+ -wal, -shm)      the database: all collected data
  corpus_pages/DOC-xx/pN.png  page images (and chart crops) rendered from the Alfa PDFs (created by corpus-parse)
  corpus_extraction/DOC-xx/   per-page extraction cache (committed; used when no VLM endpoint is set)
  input/alpha/                the 9 supplied Alfa PDFs (DOC-01..DOC-09) — image-only
  synthetic/                  CSVs generated by `synth` (clients, links, payments)
  ref/                        reference CSVs: metrics_catalog, bank_view_manual, key_numbers_to_verify,
                              alfa_search_golden, golden_set_seed, … (committed; do not delete)
  bank_view_seed.csv          placeholder seed for bank_view (committed, verified_by=seed)
```

`config/` holds the knobs (`sources.yaml`, `settings.yaml`, `models.yaml`, `series.yaml`); change
them by editing files, not code.

## 2. Steps — local run

Steps 1–8 work **without internet**.

| # | Step | pip | uv |
|---|---|---|---|
| 1 | Open a terminal in the project folder | `cd <project>` | same |
| 2 | Install | `python -m venv .venv` → activate → `python -m pip install -r requirements-dev.txt` | `uv sync` |
| 3 | Configure | `cp .env.example .env`; edit `NAFA_CONTACT`, `NAFA_ADMIN_TOKEN` (loaded automatically) | same |
| 4 | Self-test (offline, bundled fixtures) | `python -m pytest -q` → **77 passed** | `uv run python -m pytest -q` |
| 5 | Create the DB | `python -m app.cli init-db` | `uv run python -m app.cli init-db` |
| 6 | Fill with demo data | `python -m app.cli synth` | prefix `uv run` |
| 7 | Bank position (reviewed records) | `python -m app.cli bankview-seed data/ref/bank_view_manual.csv` | prefix `uv run` |
| 8 | Look at it | `python -m app.cli db-info`, `search-news "ставка"`, `quality` | prefix `uv run` |
| 9 | Start the API | `python -m app.cli serve` → http://localhost:8000/docs | prefix `uv run` |

Then, with internet, fill the DB from real sources:

| # | Step | Command |
|---|---|---|
| 10 | Test the real sources | `check-sources` — records the robots.txt fact + status per source |
| 11 | Collect once | `run-source --all` (news + rates) |
| 12 | FX history | `backfill-fx --start 2026-09-25 --end 2026-10-24` |
| 13 | Parse the Alfa corpus | `corpus-parse ./data/input/alpha` (see below), then `corpus-report` |
| 14 | Verify key numbers | `corpus-verify-key` → marks chunks verified, prints discrepancies |
| 15 | Keep collecting | `worker` in a second terminal (polls on each source's schedule) |
| 16 | Produce the deliverable files | `report --out docs/backend` → `01_…`, `02_…`, `03_…`, `04_…` |
| 17 | Optional evaluations | `search-alfa-eval` (10-query top-3), `dedup-eval pairs.csv` |

Every command is `python -m app.cli <command>` (uv: `uv run python -m app.cli <command>`).

## 3. Steps — Docker

```bash
cp .env.example .env                 # compose reads it (env_file)
docker compose up -d --build         # image: Python 3.12 + requirements + Tesseract
docker compose ps                    # api + worker "running"
curl http://localhost:8000/health    # {"status":"ok"}

# fill the volume DB (/data/nafa.db)
docker compose exec api python -m app.cli init-db
docker compose exec api python -m app.cli run-source --all
docker compose exec api python -m app.cli bankview-seed data/ref/bank_view_manual.csv
docker compose cp data/corpus_extraction api:/data/corpus_extraction        # optional: offline corpus cache
docker compose exec api python -m app.cli corpus-parse ./data/input/alpha
docker compose exec api python -m app.cli corpus-verify-key
docker compose exec api python -m app.cli db-info                           # shows /data/nafa.db

docker compose logs -f worker         # watch collection
docker compose down                   # stop; the DB is kept.  `down -v` DELETES the DB.
```

## 4. What each part does and what it writes

| Part | Reads | Writes |
|---|---|---|
| Source registry (`config/sources.yaml`) | — | `sources` |
| News connectors (SRC-01/03/04) | RSS feeds | `documents`, `clusters`, `news_fts`, `ingestion_log`, `fetch_runs` |
| Macro connectors (SRC-02 daily FX, SRC-16 key rate) | cbr.ru XML / HTML | `macro_series` |
| Manual/fallback macro (`macro-add`, M-11 from DOC-04) | command line | `macro_series` |
| Pasted news (`byo`, `POST /events/ingest`) | text or allow-listed URL | `documents` (same pipeline) |
| Alfa corpus parser | PDFs → images + VLM **or** extraction cache **or** Tesseract | `alfa_docs`, `chunks`, `chunk_fts`, `llm_calls`, `llm_cache`, `data/corpus_pages/` |
| Bank position (`bankview-seed`, `bankview-add`) | CSV / command line | `bank_view` (newest `as_of` active, older `superseded`) |
| Client loader (`load-clients`) | 3 CSV files | `clients`, `client_links`, `payments`, `load_reports` |
| Quality metrics | the logs above | `GET /quality/ingestion` (Q-23…Q-27), `GET /budget` |
| Report generator | the DB + config | `docs/backend/01..04_*.md` |

Collection flow: `source → connector → normalise → store → index → dedup/cluster → ready → log`.

## 5. Corpus extraction in one paragraph

The PDFs are image-only, so `corpus-parse` gets text from (1) the approved VLM if `LLM_*` is set,
(2) the per-page offline cache `data/corpus_extraction/<doc_id>/p<n>.json` (the "cached by file
hash, offline, once" route, used when no VLM is configured), or (3) local Tesseract OCR as the last
resort. Each page becomes `chunk` rows with `doc_id`, `page`, `as_of_date`; chart estimates never
become facts. `corpus-verify-key` checks the curated key numbers against the stored chunks and
marks reviewed chunks `verified_by=manual`. Re-run with the real VLM after filling `LLM_*`:
`corpus-parse ./data/input/alpha --force`.

## 6. Daily operation

* Keep `worker` running (or the `worker` container). It polls: Bank of Russia press every 10 min,
  Interfax and RBC every 5 min, exchange rates every 3 h, key rate every 6 h.
* Health: `GET /sources`, `GET /quality/ingestion`, or `python -m app.cli quality`.
* Back up with the online-backup command in the guides (section 8), not a plain copy while the
  worker writes.

## 7. Read before you trust the results

**Verified in this build:** the test suite (**77 passed**), live collection from the P0 sources
(Bank of Russia RSS/XML/key-rate, Interfax, RBC — 100 % of feed items parsed), a 30-day FX
backfill (the 20.10.2026 rates match the case reference exactly), the supplied Alfa corpus
(9 documents, 214 chunks), 34/34 key numbers verified with 0 discrepancies, and a 10-query search
evaluation with 10/10 expected documents in the top-3.

**Not covered here — check these yourself:**

1. **Docker** — compose was written and reviewed but not run in this environment (no Docker daemon).
2. **Approved VLM endpoint** — format, model names and RUB prices in `config/models.yaml` are
   placeholders (`0.0`); the corpus was built via the offline cache, not Qwen3-VL.
3. **DOC-10 «Commodities performance»** — not supplied; reported `missing` (no substitute made).
4. **Real participant CSV files** — not supplied; the loader is implemented and tested on synthetic data.
5. **Legal terms of use** — robots.txt facts are recorded, but the terms review (`legal.terms_checked_at`)
   is still a human task; only snippets are stored until then.
6. **Q-24 ingestion latency** — currently reflects a cold-start feed; re-measure after the worker has
   polled for a few days.
7. **Dedup thresholds and DA-owned formulas (FM-06…FM-13)** — assumptions / out of this role's scope.

See `docs/backend/acceptance_matrix.md` and `docs/backend/release_verification.md` for the full record.
